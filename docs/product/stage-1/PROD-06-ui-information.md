# PROD-06 — UI Information Catalog

## Status and Purpose

**Document status: CLOSED — Stage 1 product definition, confirmed by Mauricio after PR #7 merge.**
**Human Gate: APPROVED.** 

This document defines what information the SAT-Dengue V2 interface should expose, its product priority, and its intended source. It does not freeze a final API schema, storage model, visual layout, or scientific definition.

This document refines the information needs established by [PROD-04](PROD-04-dashboard-master-user-story.md) and the workflow in [PROD-05](PROD-05-new-period-flow.md).

Priority labels:

- **P0 — REQUIRED:** required to support the central decision and basic interpretation.
- **P1 — IMPORTANT:** materially improves interpretation, context, accessibility, or traceability.
- **P2 — OPTIONAL/LATER:** useful when scientifically and product-valid; absence must not block the core product.

Source labels:

- **INPUT:** supplied in the monthly input when the later Input Contract requires it.
- **DERIVED:** computed from validated product/data logic.
- **MODEL:** produced by the predictive model or approved post-processing.
- **PERSISTED RESULT:** stored metadata/result from completed processing.
- **REFERENCE DATA:** controlled geographic or other reference information.
- **SYSTEM:** generated by the application/runtime, such as timestamps.

## Minimum User View — REQUIRED

The core decision view must allow the user to answer these questions without interpreting raw model internals:

1. **Which department and municipality am I looking at?**
2. **What is the latest observed/reference period?**
3. **What is the current observed epidemiological context?**
4. **What is the risk signal for T+1?**
5. **What is the risk signal for T+2?**
6. **How strong is each estimate and what period does it refer to?**
7. **Is the prediction valid/available?**
8. **How fresh is the result and which model version produced it?**

Accordingly, the minimum visible product information is:

- department;
- municipality;
- reference period T;
- current observed state/context;
- T+1 target period, alert, and probability;
- T+2 target period, alert, and probability;
- explicit unavailable state when no valid prediction exists;
- endemic-channel visualization with observed cases and approved thresholds/bands;
- generation timestamp;
- model version;
- last upload timestamp when applicable.

The traffic-light color must never be the only carrier of meaning; a textual alert label is required.

## Information That Must Not Be Invented

The interface must not fabricate or infer missing values merely to complete a visual component. In particular, it must not invent:

- a zero probability for an unavailable prediction;
- a low-risk color for insufficient data;
- a projected T+1/T+2 case count when the model does not produce one;
- P25/P50/P75 or other endemic thresholds unless supplied by the approved epidemiological method;
- SHAP values or other explanations when no scientifically valid explanation exists;
- a data-upload timestamp for historical/model-training results that did not originate from a user upload;
- today's date as the prediction generation date;
- onset/continuation semantics before the target/state rules are frozen.

## Information Ownership by Layer — Product Boundary

### The model or approved post-processing may own

- predictive probability/risk score;
- approved alert category;
- applicable prediction/decision threshold;
- scientifically valid explanation output, when later approved.

### Epidemiological/data logic may own

- observed case series;
- endemic-channel bands/thresholds;
- current observed epidemiological state;
- eligibility/availability state;
- target month derivation;
- onset/continuation interpretation once formally frozen.

### The application/persistence layer may own

- generation timestamp;
- upload timestamp;
- model version;
- result origin;
- historical retrieval metadata when history is later included.

### The UI owns presentation only

The UI may format, sort, filter, navigate, and visualize approved information. It must not independently choose scientific thresholds, recompute model probabilities, fit an endemic channel, derive hidden labels, or replace missing values with plausible-looking defaults.

## Priority Decisions

### P0 — Must be available for the central workflow

- selected geography;
- current/reference period;
- current observed epidemiological context;
- T+1 and T+2 alert/risk estimate;
- probability/risk score for each horizon;
- explicit prediction availability state;
- endemic-channel observed/context view.

### P1 — Important for interpretation and usability

- freshness timestamps;
- model version;
- applicable prediction/decision threshold;
- municipal alert map and equivalent table;
- event interpretation once scientifically frozen.

### P2 — Do not block the core dashboard

- prediction history;
- dedicated climatic-context visualization;
- dedicated explainability visualization;
- advanced technical diagnostics.

## Open Decisions and Later Freeze

- **OPEN DECISION:** whether prediction/decision thresholds should be visible as exact numeric values to all users or primarily represented through approved alert semantics.
- **TO BE FROZEN IN LATER STAGE:** exact endemic-channel information, case definition, and current-state semantics.
- **TO BE FROZEN IN LATER STAGE:** exact traffic-light categories, colors, thresholds, calibration semantics, and unavailable/uncertain states.
- **TO BE FROZEN IN LATER STAGE:** explainability method and which explanation fields are scientifically defensible.
- **TO BE FROZEN IN LATER STAGE:** climatic variables, units, temporal availability, and whether they are user-facing or used only by the model.
- **TO BE FROZEN IN LATER STAGE:** final API field names and UI component layout.

This catalog defines information needs, not a final interface or API contract.
